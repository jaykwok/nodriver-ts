# API and behaviour

[简体中文](zh-CN/api.md)

Every operation is asynchronous except read-only properties and event subscriptions. Public types are exported from the root entry point `nodriver-ts`, and the build ships `.d.ts` files. CDP types come from `devtools-protocol`, which is installed with the package.

Raw CDP applications can use `attach: 'none'` and `browser.attachSession(targetId, options)`. `TargetSession` extends `Session` with `targetId`, `ended`, `endReason`, and `detach()`. See [the raw-session contract](raw-sessions.md) for lifecycle, cancellation, `observe.onSend` / `onSettle` / `onResponse`, and `connection.unansweredCount`.

## Deadlines and cancellation

`WaitOptions` combines a `timeout` in milliseconds with an `AbortSignal`. A timeout outside 0–2147483647 ms throws `RangeError`; 0 expires immediately and does not mean "wait forever".

| Operation                                            | Default deadline                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| Launching or connecting to Chrome, CDP handshake     | 30 s                                                                            |
| A single protocol command                            | 30 s; `launch({ timeout })` sets both the launch/handshake and command deadline |
| `waitForSelector`, `waitForFunction`, action polling | 10 s, polling every 50 ms                                                       |
| `inspectEnvironment`                                 | 5 s                                                                             |
| `diagnoseEnvironment`, `alignEnvironment`            | 10 s                                                                            |

`sendWith(method, { timeout, signal }, ...params)` sets a deadline and cancellation for one command. Multi-step operations share one budget: each step of a selector query (the execution-context wait and every DOM/Runtime request) gets only the remaining time, and so does each attempt of `waitForSelector()` / `waitForFunction()`. `browser.newTab(url, context, options)`, `context.newTab(url, options)` and `scope.newTab(url, options)` cover creating the tab, attaching it and the first navigation with one deadline; a tab that does not finish opening is closed, including one Chrome creates after the caller stopped waiting. Once the deadline has passed or the signal has aborted, the call returns without waiting for that close. Concurrent callers share one execution-context lookup; a caller that times out or is cancelled ends only its own wait. Releasing a query's object group has its own 1 s deadline and does not delay the caller's return.

A host-side deadline or cancellation only stops waiting. CDP commands already sent, page scripts already run and input already dispatched are neither undone nor replayed. Cleanup the library does after an operation failed or after its caller stopped waiting, such as closing a tab that did not finish opening or undoing what `clearSiteData()` set on a tab, never replaces the operation's own error; if that cleanup fails, the failure is reported through `onError` and `browser.errors`.

## Navigation and event waits

Navigation waits for `load` by default; `domcontentloaded`, `commit` and `networkidle` (Chrome's networkIdle lifecycle event) are also supported. SPA/hash navigations complete on the same-document navigation event, and BFCache restores complete on the restore event. Once a new document has committed, a same-document change such as `history.replaceState()` only updates the URL the wait resolves with; the wait still ends at the requested lifecycle event. When a document is replaced before it reaches the awaited event, as in a sign-in flow where a page submits a form or calls `location.replace()` during loading, the wait follows each new main-frame document and completes when one of them reaches the event, within the same deadline. Only the first navigation is sent; the wait resolves with the URL of the document that completed it. A document that reaches the event before it is replaced completes the wait. `reload()` completes only with a new document, and `go()` completes a same-document history navigation only when the page reaches the entry's URL.

Register waits for navigation, downloads, popups and responses before triggering the action. A closed session rejects its pending requests and event waits, and late responses are dropped. `tab.crashed` reports a crash of the page's own renderer; a crash of an out-of-process iframe does not set it. `reload()` or `goto()` recovers a crashed page: a new main-frame document clears the flag, and old handles stay invalid. After a disconnect, open a new connection; the library does not replay scripts or input.

## Queries

- A selector is a CSS string, `{ css }`, `{ xpath }` or `{ text, exact? }`.
- CSS and text queries pierce open and closed shadow roots by default; `pierce: false` turns this off. XPath follows standard semantics and does not cross shadow roots.
- Text matching collapses whitespace and, by default, returns only the smallest visible elements that do not contain a matching child.
- `Frame.query()` searches only the selected frame and never crosses into iframes. `Element.query()` is scoped to the element's subtree.
- A query walks the document and open shadow roots in a single pass inside a randomly named isolated world. When piercing (the default), closed shadow roots are found with `DOM.getDocument`. If none are found, that result is reused for the same document for up to 1 s while the structure is unchanged; if some are found, they are cached until the DOM structure changes and passed to the same single pass.
- `tab.locator(selector, options?)` and `frame.locator()` return a `Locator`: a query that runs again before each action (`click`, `hover`, `fill`, `type`, `setChecked`, `text`, `attribute`), so the action reaches the current element after a single-page app re-renders it. One timeout and signal cover finding the element and the action, reads included. If the element is replaced before the action sends a press, key or text, the action runs again on a new match; once such input was sent, a failure is reported and the action is never repeated. `element()` waits for the first match and `count()` counts current matches.
- `Element.text()`, `html()` and `attribute()` accept `{ timeout, signal }`.
- `QueryOptions` accepts `pierce`, `visible`, `limit` (10,000 matches by default), `timeout` and `signal`. Polling is not meant for high-frequency full scans of large pages.

## Evaluation and execution worlds

`evaluate()` runs in the main world by default; `{ world: 'isolated' }` uses an isolated world. DOM helpers always use a randomly named isolated world. Isolated worlds share the DOM with the page, so the page can observe DOM changes and input events.

Functions run in the browser and cannot capture host closures. Arguments are passed as one serializable value, and a `JSHandle` can be an argument. Exceptions in user scripts throw `EvaluationError`. The string form of `evaluate` / `evaluateHandle` accepts a positive `executionTimeout` in milliseconds. It maps to `Runtime.evaluate.timeout`: it limits only the initial synchronous run, cannot stop timers, requests or async continuations that were already scheduled, and is not a resource sandbox. `Element.withObject(fn)` runs `fn(objectId, group)` with a handle to the element in the isolated world; objects that `fn` creates in `group` are released together with the handle.

The library does not call `Runtime.enable`. The main world is resolved and validated through the owning frame's Document and `DOM.resolveNode`; see the [automation audit](automation-audit.md). Runtime events are therefore not delivered; sending `Runtime.enable` yourself through `cdp` delivers them but changes the detection surface. Register `addInitScript()` before `goto()`. A new OOPIF is initialized while paused and then resumed, with a watchdog as a fallback. Popups and external pages that have already started running get no guarantee that the script runs before their first script.

### Profiles

Without `userDataDir`, every launch starts with a new temporary profile that is deleted on close, unless the browser is handed off with `release()`. With `userDataDir`, the profile and everything Chrome keeps in it (cookies, storage, settings, caches) persist across launches. A profile directory serves one browser at a time: browsers that run concurrently need different directories.

`prepareProfile` runs before every launch, for temporary and persistent profiles alike, so settings written with `updateProfileSettings()` are checked and restored each time Chrome starts. Its second argument holds the launch `timeout` and `signal`, `temporary` (a profile the library created for this launch) and `empty`: always true for a temporary profile, and for a `userDataDir` true when the directory did not exist or held nothing but the library's lock files, `.nodriver.lock` and `.nodriver.lock.reclaim`. `empty` is read under the lock, before the library or Chrome writes anything else, so a check such as "a directory with data must already carry the application's marker" does not depend on the lock file's name. `updateProfileSettings(dir, { localState, preferences })` merges values into `Local State` and a profile's `Preferences` (`Default` unless another is named) and reads each file back; it cannot tell whether Chrome honours a value.

On Windows, Chrome's password manager can check whether the account has a blank password by attempting a sign-in with an empty password, and a failed attempt counts towards the account lockout policy. Chrome caches the result in `Local State`. A fixed `userDataDir` keeps that cache between launches, which makes the check less frequent but does not prevent it: a new profile, a changed Windows password or an invalidated cache triggers it again. In Chromium's source (`password_manager_util_win.cc`), the cached `password_manager.os_password_blank` value is reused only while the cache is valid: `password_manager.os_password_last_changed` is greater than zero and not earlier than the time Windows reports for the account's last password change. Otherwise the check runs again, so setting `os_password_blank` alone does not prevent it. The library ships no settings for this and makes no claim about which settings prevent the check in a given Chrome or Edge version. Verify a configuration on the target machine, for example with a dedicated test account and the Security log, before relying on it.

The lock file of a persistent profile records the PID and host name. A stale lock is reclaimed only once the owning process on this host is confirmed to have exited, and reclamation is serialized by a separate `.nodriver.lock.reclaim` file. If a process is killed during reclamation and leaves that file behind, launch fails with a clear error; delete the file manually after confirming the recorded process has exited. A leftover `DevToolsActivePort` in the profile (left when Chrome did not exit cleanly, for example because an MCP host force-killed the server) is probed: if the recorded browser still answers on its port, launch is refused; otherwise the file is deleted and launch continues. When launch fails and Chrome has exited, the error includes the exit code and stderr.

`Browser.connect({ endpoint, attach })` connects to an existing browser. `'all'` (the default) attaches to every tab; `'created'` attaches only to tabs that this client creates and their popups. Launch options have no effect on a connected browser, and `close()` only disconnects, which also ends the contexts this connection created with `proxy` (see [Environment](environment.md#proxies-and-webrtc)).

`browser.attachTarget(targetId)` attaches an existing page listed by `pageTargets`. If the page is still open after its previous session detached, it returns a new initialized `Tab`; the old object remains closed, so use the returned object. Concurrent calls for the same page share one attachment.

`ProfileInUseError`, carrying the `profile` path, is thrown when the process holding `.nodriver.lock` on this host is still alive, when another process wins the race to reclaim a stale lock, or when `DevToolsActivePort` is still served by the original browser. On Windows the library also probes Chrome's native `lockfile` for a sharing violation (`EBUSY`), so a running Chrome without a debugging port also produces this error; a leftover file that is not locked does not count as in use, and neither do permission errors. On Unix the native `SingletonLock`/`SingletonSocket` are not inspected, so without a debugging port you may get an ordinary launch-exit error instead.

`await using` closes resources on normal exit and during exception unwinding; `try/finally` with `close()` also works. `close()` is idempotent, and a `close()` that failed can be called again. Chrome launched without `detached` also ends when the host exits, including through `process.exit()` or an uncaught exception. JavaScript cannot guarantee cleanup if the host is force-killed or loses power; see [browser handoff and events](browser-handoff.md) for what remains in that case.

`await browser.release()` returns the WebSocket endpoint and gives up ownership of the process. Afterwards `owned` is `false`, and `close()` and async disposal only disconnect. An owned browser must have been launched with `detached: true` and without `virtualDisplay`; a pipe connection rejects handoff explicitly and is left unchanged. Handoff keeps the profile (a temporary one too) and `DevToolsActivePort`, and removes the `.nodriver.lock` that records the host PID. `disconnect()` does not give up ownership, and a pipe Chrome exits when its pipe closes. Without `supervised`, a host crash before handoff can leave Chrome running. See [browser handoff and events](browser-handoff.md) for a full example, cleanup responsibilities and the event API.

## Input and element actions

- Before a click, the element is scrolled into the viewport and checked for visibility, enabled state, stable position and hit-testing. A control inside a disabled `<fieldset>` counts as disabled, and a hit on the element's shadow tree or on a frame it contains counts as a hit on the element. Actions already dispatched are never replayed.
- `fill()` supports editable inputs, textareas and contenteditable elements. It writes Unicode through focus/selection and `Input.insertText`, and promises only the final text and the browser's input semantics; it does not simulate an OS IME candidate window or the clipboard.
- `select()` changes the value through the DOM and dispatches input/change.
- Physical keys support named keys, F1–F12, modifier combinations and US-layout characters (including shifted symbols).
- `Mouse.drag()` is a pointer drag; complex HTML5 DataTransfer needs your own protocol code.
- Cancellation and deadlines reject with `InputActionError`, whose `cleanup` reports how held keys and buttons were released. Element input stops when the element's frame or any ancestor frame navigates or detaches; raw Tab mouse/keyboard input watches the main frame.
- `browser.inputScope(session)` and `createInputScope(session)` group mouse, keyboard and composition calls under one deadline and report. See [Input](input.md).

## Screenshots, PDF and errors

`screenshot()` returns a Buffer; `path` is optional. Element screenshots suit axis-aligned elements; for rotated or perspective-transformed elements, take a page screenshot with an explicit clip. `pdf()` relies on Chrome's headless printing. Permission problems, experimental commands and differences between browser implementations surface as `ProtocolError`; they are not all treated as "unsupported".

## Network

`Network.enable` is sent only when needed: subscribing to `responses`, calling `waitForResponse`, calling `enable()` explicitly, or setting non-default headers/cache/offline. Each subscription or `enable()` call retries a setup that failed; one that succeeded is not repeated. `route()` and `authenticate()` use only the Fetch domain; if Chrome refuses the change on any session, they reject and restore the previous routes or credentials. `setExtraHeaders()` rejects invalid header names and values with `TypeError` before sending anything. Headers, cache and offline settings are kept, and applied to later sessions, only once Chrome accepts them. Sessions that close during these calls are skipped.

`tab.fetch(url, options?)` and `frame.fetch()` run `fetch()` in the frame's isolated world, so a request uses the page's cookies, origin, proxy and network stack and resolves relative URLs against the page; page scripts cannot see or replace it. Options take the usual request fields (`method`, `headers`, `body`, `credentials`, `mode`, `redirect`, `referrer`, `referrerPolicy`), `responseType` (`text`, `json` or `base64`) and `maxBytes` (10 MiB by default; a larger body is aborted and rejected). Every status resolves with `{ url, status, statusText, ok, redirected, type, headers, body }`; a network failure rejects with `EvaluationError`. On timeout (30 s by default) or abort the request is aborted in the page as well, and the call rejects with `FetchCancelledError`: `aborted` is `true` when the page request was aborted or ended with its document, and `false` when it had already finished or could not be reached, in which case the server may have received it. Service Workers and the page's resource timing can still observe the request.

A route handler that throws before answering is reported through `onError` and `browser.errors`, and its request is aborted. An answer Chrome refuses rejects with `ProtocolError` and leaves the route open: the handler can answer again, and a request it leaves unanswered is continued. An answer to a request Chrome no longer holds, because the page cancelled it or the route was removed, resolves without effect. Routes cover the selected Tab and its OOPIFs, but not Service Workers, the browser's own requests or other tabs. Call a response's `body()` after its content is available; CDP may refuse when the cache entry was evicted or the response was redirected.

## Tab scopes

`browser.tabScope()` and `context.tabScope()` group the pages of one task in a browser that other work shares. The scope owns the tabs opened through `scope.newTab()`, tabs passed to `adopt()`, and popups any of them open, transitively. `borrow(tab)` lends the scope a tab that outlives it, for example a start page that every task reuses: popups it opens from now on are owned and close with the scope, while the tab itself stays open. `keep(tab)` releases a page, for example one left for a person to finish; its later popups are not owned. Whether a popup is owned is decided when Chrome reports it, by its opener's role at that moment: popups a tab opened before it was adopted or borrowed are not owned, and changing a tab's role later does not change the popups it has already opened, including ones still being attached. Calling `adopt`, `borrow` or `keep` again moves a tab to that role. Roles belong to the page, so a page attached again with `attachTarget()` keeps its role. `close()` (also through `await using`) waits for tabs still opening through the scope, including tabs Chrome creates after their `newTab()` call stopped waiting, closes every owned page, including popups that open meanwhile and popups not yet attached, and leaves every other tab open. One deadline, the connection's command timeout, covers that waiting and closing: a page not closed by then is reported as a `TimeoutError` in the `AggregateError` and closes in the background, where a failure to close it is reported through `onError` and `browser.errors`. A failure to close a tab that did not finish opening through `scope.newTab()` is reported the same way, unless `close()` is waiting for that close; the tab stays owned, and `close()` tries again. Popups a page opens while `scope.newTab(url)` loads it belong to the scope. A `newTab()` that completes after `close()` started closes its tab and rejects; `close()` resolves only after that tab is closed and includes it in its result. The result lists the IDs of the pages the scope closed, including tabs that did not finish opening through `scope.newTab()`, and of the kept and borrowed tabs still open; pages that could not be closed reject with an `AggregateError`. Popups opened with `noopener` still report their opener in Chrome; popups opened by a kept or unrelated tab are never owned.

```ts
await using scope = browser.tabScope();
const tab = await scope.newTab('https://example.com');
// ... popups that the task opens are closed with the scope
scope.borrow(startTab); // stays open; its popups close with the scope
scope.keep(reviewTab); // left open for a person
```

## Virtual display

`Browser.launch({ virtualDisplay: true })` runs headful Chrome on its own Xvfb server, for Linux machines without a display. It needs the `Xvfb` program and is refused on other platforms and together with `headless: true`. Pass `{ screen: '1920x1080x24', timeout, executable }` to configure it.

The server picks a free display and reports it through `-displayfd`, so concurrent launches do not compete for a number. It does not listen on TCP and requires an MIT-MAGIC-COOKIE, written to 0600 files in a temporary directory, so other local users cannot connect. It stops after Chrome exits and its files are removed. With `supervised: true` the guardian owns both processes, which end together if the host exits. `XvfbSession.start(options)` runs a server on its own; pass `session.env` to the program that should use it, and call `session.stop()`. `release()` refuses a launch with `virtualDisplay`, as nothing would end the server once the handed-off Chrome exits; to hand off a browser on a virtual display, start the server this way and launch with `env: session.env`.

## State and storage

Cookies and storage are isolated between BrowserContexts. That isolation does not extend to the operating system, GPU or fonts.

`storageState({ include, maxBytes, path })` saves cookies, plus first-party localStorage for every HTTP(S) origin that any frame in the context has visited, including iframes and origins used by tabs that have since closed. Empty storage is not exported. Partitioned localStorage of cross-site iframes under other top-level sites is not in the snapshot. Main pages that are still open are read in place; other origins are read in one temporary tab.

The result has `version: 2`. `include: ['sessionStorage']` adds the sessionStorage of the top-level documents of open tabs, one entry per origin, taken from the first tab that shows it. `include: ['indexedDB']` adds each origin's databases to its entry: version, object stores, indexes and all records, with Date, ArrayBuffer and typed arrays, Blob and File, Map, Set, BigInt, undefined, NaN and ±Infinity kept in a tagged JSON form. Databases are read in batches on an empty intercepted page, so a page writing at the same time can produce an export that mixes before and after. A value that cannot be represented, such as a cyclic one or a stored platform object like a `CryptoKey`, fails the export. An export larger than `maxBytes` (64 MiB by default) fails with a `RangeError`.

`restoreStorage(state, { sessionStorageTab })` sets cookies first, then replaces the localStorage of each listed origin. If a main page for that origin is still open, it is written in place and readable once the call returns; other origins are written in one temporary tab. The temporary tab intercepts document requests, serves a blank page and bypasses Service Workers, so it never contacts the site, follows redirects or runs site scripts. Other open documents of the same origin receive the change asynchronously, just as with cross-tab writes in the browser.

A state with sessionStorage needs `sessionStorageTab`, a tab of the context. It visits each origin on an empty intercepted page, receives the values and ends on about:blank; navigating it to the site afterwards shows them. Listed IndexedDB databases are deleted and rebuilt at their saved version with explicit keys; other databases of the origin are left alone. The call refuses, before changing anything, while a tab of the context shows such an origin, and names the tabs. If a worker or a page outside the context still holds a connection, it fails with a `NodriverError`; that database is then deleted once the connection closes. A key generator continues from the largest restored numeric key plus one, even if the original had handed out higher keys since deleted. States without `version`, from earlier releases, can be restored.

`encryptState(state, key)` and `decryptState(bytes, key)` seal a state with AES-256-GCM. `key` is 32 bytes, or a passphrase that scrypt turns into a key, with its parameters in the file header. The header is authenticated together with the content, so a wrong key and a changed file both report `Cannot decrypt the state`.

`clearSiteData({ domains, origins, types, openTabs })` deletes the data of some sites and keeps the rest of the context, for example to log out of one site while staying logged in to another:

```ts
const result = await context.clearSiteData({ domains: ['platform.example'], openTabs: 'blank' });
// { cookies: [{ name, domain, path }], origins: [...], tabs: [...] }
```

- **Matching**: `domains` covers each domain and its subdomains; `origins` names exact HTTP(S) origins, so `http://127.0.0.1:3000` leaves the pages and storage of `http://127.0.0.1:4000` alone. Cookies have no port or scheme and are matched by domain: a cookie of a listed domain or one of its subdomains, or of exactly an origin's host, is deleted, and so is a cookie partitioned under such a site. A cookie of a parent domain, such as `.example` for `platform.example`, is shared with sibling sites and kept unless the parent is listed.
- **Types**: `types` selects `cookies`, `localStorage`, `sessionStorage`, `indexedDB`, `cacheStorage` and `serviceWorkers`; all by default. Storage is cleared for each listed origin, for `http://` and `https://` of each listed domain, and for every origin under a listed domain that this context has seen: committed by a frame, in the history of an open tab, or shown by a page of the context; origins are collected before any tab changes, including those of tabs that were already open when the browser connected. Storage of other origins under a domain, for example from an earlier run of a persistent profile, is cleared only when listed in `origins`.
- **sessionStorage** lives in each tab, and a tab keeps the sessionStorage of an origin it has navigated away from until it returns there or closes. Only an open tab can clear it, so tabs that show a matching site or once committed one count as open tabs of the site when `sessionStorage` is selected. `'blank'` clears it by loading each such origin in the tab, with document requests answered by an empty page from the library and Service Workers bypassed, so the site is not contacted and no site script runs; `'close'` discards it with the tab. A page this client has not attached is seen only while it shows a matching site, and the partitioned sessionStorage of a cross-site iframe is not reached.
- **Open tabs**: a tab with a frame of a matching site could write the data back. `openTabs: 'fail'` (default) throws before anything is cleared and names the tabs; `'close'` closes them; `'blank'` navigates them to about:blank. Pages of the context that this client has not attached, for example with `connect({ attach: 'created' })`, count too: `'fail'` and `'blank'` refuse them, and `'close'` closes them. The call covers the pages of the context that are open when it starts, attached or not, and pages opened during the call are left alone. A page still being attached is waited for. Once origins are collected, each page is handled by whether this client has it attached at that point, so a page attached meanwhile is handled as a tab and one detached meanwhile as a page this client has not attached.
- **Result**: the deleted cookies without values, the origins whose storage was cleared and the target IDs of the closed or blanked tabs and pages. If a matching cookie exists again after deletion, the call throws `ClearSiteDataError`.
- **Deadlines and failures**: `timeout` and `signal` cover the whole call, from collecting origins to the final cookie check. When the call ends, also after a timeout or abort, the request interception that `'blank'` sets on a tab stops at once; turning interception off in Chrome and undoing the Service Worker bypass then have their own 5 s deadline each. If undoing fails after the call has already failed, the call keeps its own error and the undo failure is reported through `onError` and `browser.errors`. Refusing tabs under `openTabs` throws `NodriverError` before anything changes; any other failure, a timeout or an abort throws `ClearSiteDataError`, with the original error as `cause` and `result` listing the cookies deleted, origins cleared and tabs handled so far. A step that was in progress when the call stopped is not listed and may still take effect.

Chrome refuses `Storage.clearDataForOrigin` on the browser session with `Internal error`, so the commands go to the session of an open tab of the context, or of a temporary blank tab when none is open. They do not change that page. The temporary tab is closed within the call's deadline; once that has passed, it closes after the call returns. A failure to close it then, or after the call failed, is reported through `onError` and `browser.errors`.

`Frame.storage(kind = 'local', origin?)` and `Frame.setStorage(values, kind = 'local', clear = false, origin?)` accept an expected origin. Reading, clearing and writing happen in the same script as the `location.origin` check; on a mismatch they throw `EvaluationError` and the page's storage is left unchanged.

Cookie snapshots and state files contain credentials. Where they are stored is the caller's responsibility.

## Protocol and tracing

Strict command parameter tuples, return types and event types come from a pinned version of `devtools-protocol`. Events are routed by session: `session.on(method, listener)` and `session.onAny(listener)` receive only that session's events, and run before the global `connection.events`. `connection.listenerCount` counts both.

The `trace` option of `launch()`, `connect()` and `Connection` accepts `true`, which writes each command's method, session, duration and error code or name to stderr, or a function, which receives a `TraceEntry` instead. Without the option, `NODRIVER_TRACE=1` (or `true`) enables tracing; `trace: false` disables it regardless. Parameters and results are never logged.
