# 性能基线与复验

`bun run bench:mcp` 单独运行 `benchmarks/mcp.ts`，JSON 原始结果写 stdout，进度写 stderr。它使用本地 fixture、全新临时 profile、显式 headless 和默认 sandbox，不访问外部站点。框架的产品默认值现为有界面，基准显式固定 headless 以维持既有测量条件。应在无并行测试或其他高负载任务时运行；完整功能测试的耗时不能代替这个基线。

测量分为三个工作负载：

- Chrome Pipe / WebSocket 各 3 次冷启动；预热 10 次后的 100 次 `Browser.getVersion` 往返，分别报告 p50/p95/p99 与全部样本。
- 100 / 1000 / 10000 个按钮页面，AX 预热一次后各 7 次快照。输出 limit 固定 200，分别记录完整 CDP AX 响应的节点数/JSON 字节、实际返回 JSON 字节及端到端耗时。wire 插桩另有 JSON 解析开销，计入结果；字节不含传输分隔符/帧头。底层仍读取完整 AX 树。
- 1 / 5 / 20 个独立 context，经官方 InMemory MCP 执行 fill → click → snapshot 并校验文字。每进程最多 4 context，显式提高基准池上限到最多 5 进程和 20 租约；预先创建引用，预热一轮，默认测量 5 轮，保留浏览器级串行锁。报告任务分布、吞吐、错误、控制器 CPU、Chrome CPU、内存与全部释放后的池状态。

控制器记录 `process.memoryUsage()`；Chrome 记录 CDP `SystemInfo.getProcessInfo` 返回的进程集合，Linux 从 `/proc/PID/status` 读取 VmRSS，Windows 从 Get-Process 读取 WorkingSet64。采样前已退出的进程另记 missing，报告实际采样数；不会将不可读取的进程当成已证实的零内存。Chrome 内存是这些进程的 RSS 总和，会重复计算共享页，不含未列出的 crash handler，不等于 PSS 或峰值。CPU 是控制器和该 Chrome 进程集合的累计 CPU 时间差；期间退出的进程可能未纳入。端点采样只说明有限工作负载的状态，不能用来证明没有所有类型的内存泄漏。

环境变量 `BENCH_SAMPLES`、`BENCH_ROUNDS`、`BENCH_NODES`、`BENCH_LEASES` 可调整样本数与逗号分隔的规模。输出保留 Bun/Chrome/OS/CPU/内存及方法说明；任务出错、未释放池或发送默认禁止命令会使脚本失败。p99 在低样本量时接近最大样本，不能视为稳定尾延迟。

该脚本建立本项目 TS 实现的首次基线，没有同机固定 Python nodriver 提交的对照，没有多日长稳，也没有内存下降或吞吐提升比例承诺。双平台本次观测与原始日志位置记录在开发计划中。

## 2026-10-16 首次观测

同一 Ryzen 5 5600X 主机，Bun 1.4.3；Windows Chrome 155.0.8059.80，WSL2 Ubuntu 26.04 Chrome 155.0.8059.79。WSL 配置 12 个逻辑 CPU、约 7.72 GiB 内存。两平台顺序运行，没有并行浏览器测试。以下为单次运行的中位数，不能外推所有机器或归因于某一语言/传输实现。

| ------------------------ | -----------: | ---------: | -------: | -----: |
| 冷启动，3 次，ms         |          307 |        301 |      228 |    195 |
| 预热后 RTT，100 次，ms   |        0.132 |      0.208 |    0.175 |  0.327 |
| 100 按钮快照，7 次，ms   |          9.0 |        9.9 |     12.3 |   11.1 |

| 10000 按钮快照，7 次，ms |        523.9 |      571.1 |    724.5 |  832.4 |
